# Coding Agent Harness 探索性 Demo 设计

> 日期：2026-08-08  
> 状态：已完成 brainstorming，等待用户书面审阅  
> 性质：用于走通 Superpowers 工作流的可运行粗糙 demo，不是正式课程 `SPEC.md`

## 1. 目标

实现一个 Windows 优先、Python + uv 开发的纯 CLI Coding Agent Harness。用户指定一个 Python 项目、任务、OpenAI 兼容 Base URL 和模型后，harness 能调用真实 LLM，按需读取和修改工作区内的普通文本文件，自动运行 pytest，并把失败结果整理为结构化反馈驱动下一轮修正。

demo 同时提供 Mock LLM 离线模式，用确定性测试证明主循环、工具、治理、反馈、回滚和停机由本项目代码实现，而不是依赖真实模型或提示词。

## 2. 范围

### 2.1 包含

- 单进程同步 CLI；
- 自行实现的 agent loop 与显式状态机；
- OpenAI Chat Completions 兼容客户端；
- 与真实客户端共享接口的 Mock LLM；
- 列出文件、读取文件、创建普通文本文件、精确文本替换；
- 修改后自动运行固定的 `uv run pytest -q`；
- 结构化测试反馈与无进展检测；
- 路径围栏、权限分级、高风险审批和禁止项；
- 逐文件恢复记录、原子写入与任务级回滚；
- 会话内记忆和可选的最小跨会话项目摘要；
- 离线单元测试、集成测试与三项机制演示。

### 2.2 不包含

- WebUI；
- 通用 PowerShell 或任意 shell 工具；
- 删除、移动、重命名文件；
- 操作系统级沙箱；
- 多 Agent、多进程、事件总线和插件系统；
- Python/pytest 之外的语言与测试框架；
- 自动 Git commit、reset、checkout、branch 或 PR；
- 正式分发、CI、操作系统钥匙串/加密存储等正式凭据治理和课程全量交付物。

## 3. 关键设计决定

| 事项 | 决定 |
|---|---|
| 技术栈 | Python + uv |
| 产品形态 | Windows 优先的纯 CLI |
| 架构 | 模块化单进程状态机 |
| 重点维度 | 反馈闭环 |
| 客观信号 | pytest 退出码与输出 |
| 修改方式 | 原项目内直接修改，不复制整仓 |
| 恢复方式 | 只保存本次触碰文件的原始内容 |
| 审批策略 | 普通受控操作自动执行，仅高风险暂停 |
| 禁止策略 | 越界和破坏性操作直接拒绝，不提供强制绕过 |
| Mock 演示 | `clamp()` 失败、反馈、修正、通过 |
| 默认结束策略 | 成功保留；失败或中断回滚 |

## 4. 架构

```text
用户
 |
 v
CLI / Config
 |
 v
AgentLoop / SessionState
 |
 +---- LLMClient -------- OpenAICompatibleClient / MockLLMClient
 +---- ContextBuilder ---- 任务 / 工具协议 / 观察 / 反馈 / 压缩
 +---- ActionParser ----- 模型输出 -> Action
 +---- PolicyEngine ----- ALLOW / CONFIRM / DENY
 +---- ToolDispatcher --- 列出 / 读取 / 创建 / 精确替换 / pytest
 +---- FileTransaction -- 哈希 / 恢复记录 / 原子写入 / 回滚
 +---- TestFeedback ----- pytest 结果 -> Feedback
 `---- MemoryStore ------ 会话历史 / 可选项目摘要
```

整个 harness 只运行一个同步 Python 进程。CLI 负责输入输出；AgentLoop 只协调状态；ContextBuilder 负责组织发送给模型的最小上下文；安全判定、文件操作、测试和反馈分别由独立模块承担。

真实 LLM 与 Mock LLM 必须实现同一个 `LLMClient` 接口并进入同一个 AgentLoop。Mock 模式不得拥有简化版或旁路循环。

## 5. 核心数据对象

| 对象 | 主要字段与职责 |
|---|---|
| `Action` | 动作类型、相对路径、参数、模型给出的说明 |
| `PolicyDecision` | `ALLOW`、`CONFIRM` 或 `DENY`，以及规则编号和原因 |
| `Observation` | 工具是否成功、文件内容或工具摘要、错误信息 |
| `Feedback` | 反馈类别、测试状态、退出码、摘要、输出尾部、稳定指纹 |
| `SessionState` | 当前状态、轮数、动作历史、最后测试、触碰文件和失败计数 |
| `RunResult` | 成功/失败、停止原因、修改文件、测试结果、回滚结果 |

模块通过这些明确对象通信，不依赖随意拼接的字典作为内部协议。

## 6. 状态机

核心状态为：

```text
INITIALIZING
  -> REQUESTING_ACTION
  -> VALIDATING_ACTION
  -> WAITING_APPROVAL（仅高风险）
  -> EXECUTING
  -> VERIFYING（代码发生修改时）
  -> FEEDBACK
  -> REQUESTING_ACTION / COMPLETED / FAILED
```

强制规则：

- 未通过 PolicyEngine 的动作不能调用工具；
- 每轮只接受一个动作；
- 创建或修改文件后由 harness 自动进入 pytest 验证；
- 发生过代码修改时，最近一次 pytest 未通过就拒绝 `finish`；
- 动作格式错误、策略拒绝、工具错误和测试失败均形成反馈；
- 达到轮数、无进展或安全状态不确定时进入 `FAILED`；
- Mock LLM 与真实 LLM 遵守完全相同的状态转换。

## 7. CLI 与配置

概念调用方式：

```powershell
uv run rough-harness run `
  --workspace D:\Projects\example `
  --base-url https://njusehub.info/v1 `
  --model deepseek-v4-flash `
  "修复当前失败的单元测试"
```

API Key 默认通过隐藏提示输入，只保留在当前进程内存；也可从专用环境变量读取。CLI 不回显 Key，不把 Key 写入运行摘要。

默认配置：

- 最大 6 个 LLM 动作轮；
- LLM 临时网络错误最多重试 2 次；
- pytest 超时 60 秒；
- 连续 3 次动作格式错误即失败；
- 相同动作和相同反馈连续出现 2 次即判定无进展；
- 单轮普通修改最多 3 个文件、约 200 行；
- 单个普通文本文件最大 256 KiB，超过后提升为高风险；
- pytest 输出默认只保留末尾 12,000 个字符。

这些值允许通过 CLI 或普通配置覆盖；修改依赖、测试、CI 等配置文件本身属于高风险操作。

## 8. 动作与工具

真实客户端通过 Chat Completions 的 function/tool calling 暴露动作协议。ActionParser 只接受一轮中的第一个且唯一一个工具调用；没有工具调用时只允许结构化 `finish`，多个工具调用或混合文本不会执行。

第一版允许模型请求：

- `list_files`：列出工作区内允许的文件；
- `read_file`：读取一个普通文本文件，并返回内容及 SHA-256；
- `create_file`：创建一个不存在的普通文本文件；
- `edit_file`：使用 `expected_sha256`、`old_text` 和 `new_text` 做精确替换；
- `finish`：请求结束任务。

`edit_file` 仅在以下条件全部成立时写入：

- 当前 SHA-256 与模型读取时一致；
- `old_text` 恰好出现一次；
- 路径、文件类型和修改规模通过策略检查；
- 风险级别为允许，或高风险已获用户批准。

pytest 不由模型提供命令。任何成功的创建或修改都会触发 harness 内置的固定测试命令。

## 9. 一次完整数据流

1. CLI 规范化工作区，拒绝磁盘根目录、用户主目录和无效目录。
2. Config 加载 Base URL、模型、测试命令、限制和 API Key。
3. SessionState 记录任务、顶层文件列表、工具协议和可选项目摘要。
4. ContextBuilder 选择任务、最近观察、最后反馈和仍相关文件内容，超出预算的旧观察只保留摘要。
5. LLM 每轮返回一个结构化动作。
6. ActionParser 校验动作名称、必填字段和额外参数。
7. PolicyEngine 产生允许、审批或拒绝决定。
8. ToolDispatcher 只执行已允许的动作。
9. 读取动作形成 Observation 并进入下一轮。
10. 写动作先建立文件恢复记录，再原子写入，随后自动运行 pytest。
11. TestFeedback 把退出码、失败测试、摘要和输出尾部整理为 Feedback。
12. 测试失败时保留当前修改，Feedback 回灌给下一轮以便继续修正。
13. 测试通过且 LLM 请求 `finish` 时成功结束；失败预算耗尽时统一回滚。

## 10. 反馈闭环

反馈至少包含：

- `kind`：测试失败、测试超时、工具错误、策略拒绝等；
- `passed`：测试是否通过；
- `exit_code`：pytest 退出码；
- `failed_tests`：能够可靠提取时的失败测试；
- `summary`：简短结果；
- `output_tail`：截断后的原始输出；
- `fingerprint`：用于识别重复失败的稳定摘要。

解析器只能填写可靠获得的信息，不能从模糊文本中编造预期值、实际值或失败原因。

反馈指纹由稳定字段生成。连续两轮动作签名和反馈指纹均相同，状态机判定没有进展，停止继续调用 LLM 并回滚。

## 11. 治理与安全边界

### 11.1 自动允许

- 工作区内普通文本文件的列出与读取；
- 小范围普通 Python 源码或测试补丁；
- 固定 pytest。

### 11.2 高风险审批

- 修改依赖、锁文件、CI、构建或测试配置；
- 修改启动前已有未提交变化的文件；
- 单轮超过 3 个文件、200 行改动，或单文件超过 256 KiB；
- 新增代码包含明显的进程、删除、网络、动态执行或系统修改能力；
- 策略不能确定风险的文件类型。

### 11.3 永久禁止

- 工作区外路径、绝对外部路径和 `..` 越界；
- `.git/`、`.env`、常见私钥和凭据文件；
- 符号链接、Windows junction 和其他重解析点；
- 二进制和非普通文件；
- 删除、移动和重命名；
- 任意 PowerShell 或模型自定义命令；
- 把磁盘根目录或用户主目录作为工作区。

已有文件需要解析最终真实路径并检查沿途重解析点；新文件需要对父目录执行同样检查。策略拒绝必须发生在工具调用之前。

危险代码静态扫描只负责提升审批，不能宣称等同操作系统沙箱。pytest 仍以当前 Windows 用户权限运行；demo 只应处理可信项目。

## 12. 文件事务与恢复

任务第一次触碰文件时保存原始内容、原始哈希和原始存在状态。同一文件后续修改不覆盖最初恢复记录。恢复材料存入操作系统临时目录下独立的 `rough-harness/<run-id>` 目录，而不是复制整个仓库。

写入采用同目录临时文件和原子替换。测试中间失败时保留当前内容供下一轮修正；任务成功时清理恢复记录并保留修改；任务失败、用户中断或内部异常时恢复到任务开始前。本轮新建文件可以由事务管理器内部移除，这不向 LLM 暴露删除工具。

成功结束或完整回滚后清理该次临时恢复目录。回滚失败时不得声称恢复成功，也不得删除仍有用的恢复材料。CLI 列出未恢复文件、恢复材料位置，并返回专门的非零退出码。

## 13. 记忆

会话记忆始终存在于内存，保存任务、动作、观察、反馈、轮数和修改记录。旧观察超出上下文预算时只保留摘要、最近反馈和仍相关的文件内容。

最小跨会话记忆作为可选功能实现：只保存用户通过参数明确提供的项目说明，以及成功运行后的 `RunResult` 摘要；模型不能自行写入任意记忆。不保存完整对话、API Key 或文件全文。该功能默认关闭；启用时写入用户明确指定的状态文件，并按高风险配置写入处理。

## 14. 错误与停机

| 情况 | 处理 |
|---|---|
| 参数、工作区或配置无效 | 调用 LLM 前停止 |
| API 鉴权失败 | 停止；若已有修改则回滚 |
| 临时网络失败 | 最多重试 2 次，随后失败并回滚 |
| 动作格式错误 | 回灌；连续 3 次后失败 |
| 策略拒绝 | 回灌拒绝原因，不调用工具 |
| 文件哈希变化 | 拒绝覆盖并要求重新读取 |
| 精确替换不唯一 | 回灌工具错误 |
| pytest 失败 | 结构化回灌，继续修正 |
| pytest 超时 | 终止测试进程树并回灌 |
| 最大轮数或无进展 | 失败并回滚 |
| 用户中断或内部异常 | 停止并回滚 |
| 回滚不完整 | 保留恢复材料并返回专门错误 |

退出码约定：`0` 为成功，`1` 为任务失败但已回滚，`2` 为输入或配置错误，`3` 为回滚不完整。

## 15. 测试策略

默认一键测试命令为 `uv run pytest`。核心测试不依赖网络、真实 API Key、模型随机性或用户真实项目。

### 15.1 单元测试

- ActionParser：正确动作、未知动作、缺参、多余参数、非 JSON；
- PolicyEngine：允许、审批、拒绝、越界、凭据、重解析点和危险能力；
- FileTransaction：哈希冲突、精确替换、原子写入、新文件、成功提交和失败回滚；
- TestRunner：通过、失败、超时、进程终止和输出截断；
- TestFeedback：可靠提取、保守降级、稳定指纹；
- AgentLoop：强制测试、finish 门禁、最大轮数、格式错误、无进展和中断。

### 15.2 Mock LLM 集成测试

集成测试使用 pytest 临时目录、真实文件工具、真实 pytest、真实反馈和真实状态机，只替换 LLM。

三项确定性机制演示：

1. Mock LLM 请求越界或破坏性动作；护栏在工具调用前拒绝。
2. Mock LLM 首次给出错误 `clamp()` 修改；真实 pytest 失败；收到反馈后给出不同的正确修改；pytest 通过后完成。
3. Mock LLM 重复无效修改；相同反馈指纹连续出现两次；状态机以 `no_progress` 停止并恢复原文件。

### 15.3 真实 API 冒烟测试

真实 API 仅用于手动检查 OpenAI 兼容调用与 CLI 端到端接线，不进入默认测试和 CI，不作为确定性正确性证据，也不重新探测用户已验证的 API 协议。

## 16. 验收标准

- CLI 能接收工作区、任务、Base URL、模型和 API Key；
- 真实 LLM 与 Mock LLM 共用 AgentLoop；
- LLM 不能绕过 ActionParser、PolicyEngine 或固定测试命令；
- 允许的读取、创建和精确替换正常工作；
- 越界与禁止动作在工具调用前被拒绝；
- 修改后自动运行 pytest；
- 测试失败形成结构化 Feedback 并进入下一轮；
- 发生修改后，测试未通过不能完成；
- 无进展和预算上限能可靠停止；
- 成功保留修改，失败或中断默认回滚；
- 三项 Mock LLM 机制演示稳定通过；
- `uv run pytest` 可一键离线运行核心测试。

## 17. 已知限制与有意偏离

- 直接运行 pytest 不是系统级隔离，不能保证抵御恶意项目；
- 静态危险能力扫描只能提示风险，不能证明代码安全；
- 只支持 Windows 优先、Python 项目和 pytest；
- 精确文本替换比完整补丁能力弱，但更容易确定性校验；
- 本次在 `main` 上推进，不创建新分支或 worktree；
- 本次不执行正式课程所需的 WebUI、分发、CI、subagent、PR 和完整凭据治理；
- 当前目录含临时测试 Key 的早期提交，不可作为正式公开课程仓库历史；
- 正式项目需要在干净目录中重新执行完整 Superpowers、TDD、worktree、subagent、评审和交付流程。

## 18. 设计完成后的流程

用户书面审阅本文件并批准后，调用 Superpowers `writing-plans` 将设计拆成小任务和验证步骤。实现阶段按 TDD 先写失败测试、观察失败，再写最少实现使其通过。设计批准前不编写 harness 实现代码。
