# FBW v0.1.0 课程交付发布设计

日期：2026-08-13

## 1. 目标与定位

在不实现 WebUI 的前提下，完成 FBW Coding Agent Harness 的其余课程交付收尾，并通过现有 GitHub Actions 产出首个正式 Windows x64 Release `v0.1.0`。

本轮必须区分两种结论：

- **软件分发结论**：纯 CLI 已具备测试、凭据治理、单文件构建、SHA 校验和 hosted clean Windows 验收，可以发布 `v0.1.0`；
- **课程清单结论**：课程原文要求 WebUI，而用户明确决定不实现，因此不得声称课程清单 100% 合规。

## 2. 已有基线

- Python 包版本和 `fbw_harness.__version__` 均为 `0.1.0`；
- GitHub/NJU `main` 为同一规范历史，历史秘密扫描通过；
- GitHub 与 NJU 最新 CI 均由用户确认绿色；
- GitHub hosted `windows-latest` 已完成单文件 EXE、SHA、受限 PATH、离线 demo 和无凭据状态验收；
- 学校真实 API 已完成一次受控 clamp 修复；
- 当前没有 tag 或 GitHub Release；
- `REFLECTION.md` 尚未提交，且课程要求正文必须由学生本人撰写。

## 3. 方案选择

采用 **tag 驱动的现有 GitHub Actions 自动发布**。

未采用的方案：

- 手工上传既有 workflow artifact：tag、源码和二进制的对应证据较弱；
- 本机重新构建后手工上传：依赖开发机环境，可复现性和审计性较弱。

## 4. 发布范围

### 4.1 包含

- Git tag：`v0.1.0`；
- GitHub Release：`v0.1.0`；
- 附件：`fbw-harness.exe`、`fbw-harness.exe.sha256`；
- Release 说明：Windows x64、纯 CLI、SHA 校验、首次凭据配置、主要限制；
- 发布准备和发布结果的文档/过程证据；
- GitHub 与 NJU 的 main/tag 同步。

### 4.2 不包含

- WebUI、终端常驻 REPL 或 Codex CLI 式交互输入框；
- macOS/Linux 发行物；
- Authenticode 代码签名；
- 对实体 Windows Explorer/SmartScreen 行为的保证；
- 由 AI 生成 `REFLECTION.md` 正文。

## 5. 发布流程

### 5.1 发布准备 PR

在隔离 worktree 中更新 README、PLAN、AGENT_LOG 和发布清单：

- 将旧的“不可发布”改为“纯 CLI 软件可以发布，但 WebUI 课程项未满足”；
- hosted clean Windows 作为核心离线分发证据；
- 实体 Windows、SmartScreen 和未签名状态继续作为非阻断已知限制；
- 记录用户对 `v0.1.0` 和 WebUI 偏离的明确决定；
- 不创建虚假的 WebUI 豁免或 `REFLECTION.md` 完成声明。

准备 PR 必须通过双重秘密扫描、全量 pytest、Ruff 和 GitHub CI，合并后再打 tag。

### 5.2 tag 自动发布

在合并后的绿色 `main` 创建 `v0.1.0` tag，并推送到 GitHub。现有 release workflow 负责：

1. 运行 unit-test job；
2. 扫描完整 Git 历史；
3. 使用 PyInstaller 构建单文件 EXE 与 SHA；
4. 执行 EXE `--help` 和 `demo all`；
5. 上传 workflow artifact；
6. 创建 GitHub Release 并附加 EXE 与 SHA。

任一步失败都不得将该版本记录为发布成功。保留失败 run 和 tag 供诊断，不覆盖同名 tag；修复必须使用新提交，并在必要时改用新的 patch 版本。

### 5.3 发布后验收与证据 PR

Release 创建后：

- 核对 tag 指向预期 main commit；
- 下载 Release 附件；
- 用附件中的 SHA 文件复核 EXE；
- 运行 `--help`、`demo all`、两次无凭据 `credential status`；
- 记录 Release URL、workflow run、commit、附件名称和验证结果；
- 用小型证据 PR 更新 README、PLAN、AGENT_LOG 和发布清单；
- 合并后同步 GitHub/NJU main，并将 `v0.1.0` tag 推送到 NJU；
- 确认最终 GitHub/NJU CI 绿色后清理 worktree 和功能分支。

## 6. 安全与失败处理

- 发布前继续运行当前树与完整历史秘密扫描；日志不得输出匹配内容；
- Release 不包含 API Key、环境文件、JSONL、项目记忆或真实 API 请求/响应；
- 发布验收只运行离线 demo 与无凭据状态，不在云端录入 Key；
- SHA 不用于证明不同构建字节级可复现，只证明下载附件与同次发布校验文件一致；
- EXE 未签名必须在 README 和 Release 说明中明确；
- 不重写或移动已经公开的 tag；失败后通过新提交和新版本恢复；
- 不因发布完成而把 WebUI、实体 SmartScreen 或学生反思报告标为已完成。

## 7. `REFLECTION.md` 边界

课程要求反思报告由学生本人撰写，禁止 AI 代写。本轮不生成正文或伪造完成状态。学生完成初稿后，AI 仅可检查字数、章节覆盖和表达，并在文档中标注辅助润色。

## 8. 验收标准

- 发布准备 PR 合并，GitHub 两类 CI 绿色；
- `v0.1.0` 指向经验证的 main commit；
- tag workflow 的测试、历史扫描、构建、EXE 冒烟和 Release job 全部成功；
- GitHub Release 页面可访问，并含 EXE 与 SHA 两个附件；
- 下载附件 SHA 复核通过，EXE `--help`、`demo all`、无凭据状态通过；
- 发布证据 PR 合并，GitHub/NJU main 同步，NJU 最终 pipeline 绿色；
- WebUI 与 `REFLECTION.md` 状态如实记录，没有声称课程清单完全合规；
- 临时 worktree 和功能分支完成清理，根仓库只保留 main 与三份未跟踪进度文件。
